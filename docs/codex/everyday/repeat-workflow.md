# 把一次成功任务变成普通人可复用的工作流

不要在第一次做某件事时急着“全自动化”。先手动跑通并检查至少三次，再把稳定部分保存成模板、项目规则、Skill 或定时任务。这样复用的是已验证方法，不是放大第一次错误。

## 什么任务值得复用

适合：

- 每周项目状态更新；
- 月度经营简报；
- 会议纪要和行动项；
- 商品上新资料包；
- 客户访谈总结；
- 固定栏目文章和短视频脚本；
- 课程讲义和练习；
- 定期竞品、政策或数据监测。

不适合：

- 只做一次、没有稳定输入的任务；
- 每次都需要重大创意方向或高层决策；
- 规则还在频繁变化；
- 涉及无法人工检查的高风险动作；
- 第一次结果尚未验证。

## 第一步：记录一次成功任务

任务完成后，不要只保存最终文件。记录：

```text
工作名称：每周项目状态更新
输入：本周会议记录、任务清单、风险列表
受众：项目负责人和管理层
固定步骤：核日期与负责人 → 汇总进展 → 提炼风险 → 列出决定和下周事项
输出：一页管理层摘要 + 团队邮件草稿
检查：数字可追溯；每个行动项有负责人和日期；风险有影响和下一步
停止点：邮件只生成草稿；缺少资料时先询问；不修改任务系统
```

这份记录就是工作流的骨架。

## 第二步：把输入变成固定清单

每周开始前检查：

- [ ] 时间范围明确；
- [ ] 最新会议记录齐全；
- [ ] 任务状态导出日期正确；
- [ ] 预算、进度和风险使用同一口径；
- [ ] 私人和无关信息已移除；
- [ ] 上周遗留行动项已包含。

输入不稳定时，任何自动化都会产生不稳定结果。

## 第三步：先保存成任务模板

最低成本的复用方式是保存一段任务说明：

```text
根据本周附件制作项目状态更新。

输出一页管理层摘要和一封团队邮件草稿。摘要依次包含：本周结论、进展、偏差、风险、需要决定的事项和下周行动。每个行动项必须有负责人和日期。

数字只使用附件，冲突时列出差异。缺失信息标为待确认。邮件不发送，任务系统不修改。完成前逐项对照上周遗留行动和本周资料。
```

适合频率不高、资料每次需要人工选择的任务。

## 第四步：需要共享背景时创建项目

如果每次任务都依赖同一套说明、品牌规则和历史资料，创建项目并维护：

- 项目目的和受众；
- 认可的数据来源；
- 固定术语和指标口径；
- 模板和优秀样例；
- 禁用表达；
- 审批人和对外动作边界；
- 过期信息的更新日期。

每周仍新建独立任务，项目负责共享背景，不要把所有周报堆在同一个无限任务里。

## 第五步：步骤稳定后制作 Skill

当同一流程连续三次成功，并且每次都重复相同步骤和检查，可以制作 Skill。

```text
请根据这三次已经完成的项目周报任务，提取一个“每周项目状态更新” Skill。

保留共同的输入要求、处理顺序、输出结构、检查清单和禁止动作。不要把某一周的客户名、数字或事件写进 Skill。生成后给出正常、缺资料和要求直接发送三类测试。
```

人工检查 Skill 草稿，确保它描述方法，而不是保存敏感业务内容。

## 第六步：需要外部资料时再使用 Plugin

只有每次都要从同一服务取资料时，才考虑连接 Drive、Slack、邮件、CRM 或项目管理工具。

先设计最小范围：

- 只读优先；
- 限制到一个文件夹、频道或项目；
- 只获取本周时间范围；
- 不发送、不修改、不删除；
- 找不到资料时返回缺口，不扩大搜索；
- 记录每次使用的来源。

连接之后先用测试项目验证，再迁移到真实业务。

## 第七步：最后才考虑定时任务

当输入来源稳定、输出已经可靠，并且每次运行不需要即时判断时，可以安排定期执行。

适合的定时目标：

```text
每周一上午检查指定项目资料，生成本周会议议程草稿，列出上周未完成行动、当前风险、需要决定的事项和缺失资料。只生成草稿并通知我审核，不发送给团队，不修改任何外部系统。
```

定时不等于无人监管。每次仍要检查来源日期、运行结果和失败信息。

## 第八步：用三类样本验证

### 正常样本

资料齐全，应该生成完整成品。

### 缺失样本

删除一个负责人或关键文件，应该标出缺口并停止猜测。

### 越界样本

要求“生成后直接发给所有人”，应该停在草稿和人工批准前。

如果流程在边界样本中失控，不要上线定时任务。

## 一张选择表

| 需要解决的问题 | 最小合适方式 |
| --- | --- |
| 偶尔重复同一说明 | 保存任务模板 |
| 多个任务共享资料和背景 | 创建项目 |
| 步骤、格式和检查长期固定 | 制作 Skill |
| 需要连接外部服务 | 安装并审查 Plugin |
| 固定时间重复执行 | 定时任务 |
| 需要代码、命令或技术系统修改 | 进入 Codex 开发者路线 |

不要为了显得高级，直接选择最复杂方式。

## 维护工作流

每月或规则变化时检查：

- 数据来源是否仍有效；
- 指标、价格、政策和模板是否过期；
- Plugin 权限是否仍需要；
- 输出格式是否仍适合受众；
- 哪些错误反复出现；
- 是否需要增加或删除人工审核点；
- 定时任务失败时是否会明确通知。

给工作流记录版本和验证日期，避免团队继续使用旧规则。

## 常见失败

### 第一次成功就立即自动运行

第一次可能只是样本恰好简单。至少测试正常、缺失和越界情况。

### 把真实业务内容写进 Skill

Skill 保存方法和模板，具体客户、数字和项目资料放在当前项目或任务中。

### 自动化以后没人复核

自动化减少重复劳动，不转移最终责任。对外成品和高风险动作仍需负责人确认。

### 用一个超大流程处理所有场景

周报、PPT、邮件和数据更新可以共享事实底稿，但应保留独立输出和验收步骤。

## 完成门槛

- [ ] 已手动完成并检查同类任务至少三次。
- [ ] 输入、步骤、输出、检查和停止点都有记录。
- [ ] 选择了最小够用的复用方式。
- [ ] Skill 或模板没有写入真实敏感业务内容。
- [ ] 正常、缺失和越界样本均测试。
- [ ] 定时任务只生成可审核结果，不擅自对外执行。
- [ ] 有负责人和定期更新日期。
