# Codex 是什么：先完成一次只读项目体检

如果你只把 Codex 当成“会写代码的聊天框”，很快就会遇到两个问题：它不了解真实项目时容易猜，它拥有工具权限时又可能做得比你预期更多。本页用一次不修改文件的项目体检，让你先看懂 Codex 的工作方式和边界。

> 如果你不写代码，目标是 PPT、Word、Excel、电商、研究或内容创作，不要从 Git 仓库体检开始。当前官方产品把这类可审核成品优先放在 ChatGPT Work；请进入 [普通人完整学习路线](/codex/everyday/)。本页以下内容是开发者路线。

## 先给出一个工程化定义

Codex 是能围绕一个目标反复执行“读取上下文、制定下一步、调用工具、观察结果、继续修正”的智能代理。它和普通问答最大的区别，不是更会背代码，而是能够进入你的工作环境并产生可检查的结果，例如：

- 搜索仓库并画出真实调用链；
- 运行测试，读取失败输出，再定位问题；
- 修改多个文件并展示 Git diff；
- 打开本地页面，检查界面是否真的可用；
- 读取文档、表格或截图，生成新的交付文件；
- 通过 MCP 或插件访问经过授权的外部系统。

因此，使用 Codex 时最重要的对象不是“答案”，而是三个东西：**任务边界、执行证据和最终差异**。

## 四种常见入口分别解决什么问题

| 入口 | 最适合的任务 | 你主要检查什么 |
| --- | --- | --- |
| ChatGPT 桌面应用中的 Codex | 多任务、长任务、文件预览、浏览器验证、Git 审查 | 任务进度、文件预览、diff、终端结果 |
| Codex CLI | 终端优先、服务器、脚本、CI、精确复现 | 命令输出、工作树、退出码、JSONL |
| IDE 扩展 | 围绕当前文件或选中代码快速修改 | 编辑器上下文、局部 diff、诊断信息 |
| Codex cloud | 隔离环境中的并行任务、远程实现和 PR | 云环境配置、任务 diff、云端验证 |

入口不同，底层目标相同：让代理在可控环境里完成工作，再由你检查证据。

## 实操：给现有项目做一次只读体检

选择一个你熟悉的 Git 仓库。先在终端记录现状：

```bash
cd /path/to/your-project
git status --short --branch
```

然后在 Codex App 打开该目录，或从仓库根目录运行：

```bash
codex --sandbox read-only
```

发送下面这段任务：

```text
只做只读项目体检，不修改任何文件，也不要安装依赖。

请基于仓库中的真实文件回答：
1. 这个项目解决什么问题，主要入口在哪里；
2. 启动、测试、构建命令分别是什么，证据来自哪些文件；
3. 一次典型请求或用户操作会经过哪些模块；
4. 当前最需要我人工确认的三个风险是什么；
5. 列出你实际读取过的关键文件路径。

如果信息不足，请明确说缺什么，不要根据常见框架猜测。
```

### 你应该看到什么

合格结果应当引用项目里的真实路径，例如 `package.json`、`pom.xml`、`go.mod`、入口文件或部署配置，而不是只说“这看起来像一个常见的前后端项目”。

继续追问一个你能验证的问题：

```text
把“启动命令”的判断逐条对应到配置文件中的字段，并说明哪些命令你还没有实际运行。
```

这一步用来区分三种信息：

- 文件里明确写着的事实；
- Codex 根据代码结构做出的分析；
- 尚未通过运行验证的推测。

## 完成后做工作树核对

退出任务后再次运行：

```bash
git status --short
```

输出应当与开始前一致。如果出现新文件或修改，先用 `git diff` 和 `git status --short` 查清来源，不要直接执行清理命令。

## 哪些任务适合交给 Codex

优先选择具备以下特征的任务：

- 有明确输入，如仓库、错误日志、截图、数据文件或需求文档；
- 有可观察结果，如测试通过、页面行为、生成文件或 Git diff；
- 可以限定修改范围；
- 失败后能够回退或重新运行；
- 重要结论可以被代码、命令或来源验证。

不适合直接全自动执行的任务包括：需求本身没有定论、生产数据不可恢复、涉及付款或公开发布、需要代表你作法律或商业承诺，以及没有任何验收标准的“帮我优化一下”。

## 三个常见误区

### 误区一：模型越强，就越不需要上下文

模型可以主动搜索项目，但它不知道哪条业务约束只存在于团队经验里。把关键限制写进任务或 `AGENTS.md`，比让它事后猜测更可靠。

### 误区二：看到完整代码就等于问题已经解决

代码只是候选方案。测试、构建、运行时日志、浏览器行为和数据检查才是证据。

### 误区三：给满权限可以提高成功率

权限只决定“能不能做”，不决定“该不该做”。新手应先使用只读或工作区写入，只有在确实需要时才扩大网络或目录范围。
